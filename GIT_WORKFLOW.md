# PRIME Electronics — Git workflow и передача клиенту

Этот репозиторий — рабочий монорепозиторий из трёх исходных клиентских репозиториев:

- `ecommerce-backend/` — backend;
- `e-commerce/` — storefront;
- `e-commerce-admin/` — admin.

Корневые dev-файлы (`dev.cmd`, `dev.ps1`, `setup-dev.ps1`, `docker-compose.dev.yml` и т.п.) нужны только для локальной работы и клиенту не передаются.

## Базовое правило

Существующую бизнес-логику не рефакторим и не переписываем без прямой необходимости по согласованной задаче. Изменения должны быть минимальными и локальными.

## Ветки

Каждая отдельная клиентская задача выполняется в своей ветке от актуального `main`:

```text
task/<короткое-название>
```

Примеры:

```text
task/blog-publish-date
task/static-pages
task/article-products
```

После локальной проверки и подтверждения задача сливается в `main`.

## Коммиты

Не смешивать несвязанные изменения и по возможности не смешивать разные клиентские репозитории в одном коммите.

Формат:

```text
feat(backend): add scheduled blog publication
feat(admin): add publication date controls
feat(site): render scheduled article metadata
fix(backend): preserve existing author value
```

Допустимые scopes:

- `backend`
- `admin`
- `site`
- `dev` — только наша локальная инфраструктура

Это позволяет потом однозначно увидеть, где и зачем менялся файл.

## Что считается клиентскими изменениями

Файл `.client-base` хранит SHA исходного импортированного состояния клиентского кода. Все изменения внутри трёх папок после этого SHA считаются нашими изменениями для передачи.

Локальная инфраструктура в корне автоматически исключается, потому что экспорт идёт отдельно по каждой из трёх папок.

## Экспорт клиенту

Из корня Windows:

```powershell
.\export-client.ps1
```

Скрипт создаст каталог:

```text
.client-delivery/YYYYMMDD-HHMMSS/
```

Внутри будут отдельные patch-series:

```text
backend/
site/
admin/
```

Каждый `.patch` — обычный Git commit, подготовленный через `git format-patch` с путями относительно соответствующего исходного репозитория.

В клиентском репозитории серия применяется так:

```bash
git checkout -b feature/<task-name>
git am path/to/*.patch
```

В результате клиент получает нормальную историю Git-коммитов с нашими сообщениями, а не архив файлов.

## Перед каждой передачей

1. Убедиться, что `main` содержит только проверенные клиентские изменения.
2. Выполнить локальную проверку сайта, админки и backend.
3. Запустить `export-client.ps1`.
4. Просмотреть `SUMMARY.txt` в каждой папке экспорта.
5. Применить patch-series в актуальные клиентские репозитории поверх их свежих веток.

Если клиентская команда за это время изменила те же строки, `git am` остановится на конфликте. Конфликт решается уже относительно их актуального кода — без потери нашей отдельной истории изменений.
