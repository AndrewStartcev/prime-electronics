## PE-01 — Галерея изображений товара

**Приоритет:** 🟢 P3  
**Статус:** TODO  
**Зона:** `e-commerce`

### Проблема

Если у товара много изображений, миниатюры выводятся длинным вертикальным столбцом. Из-за этого блок карточки становится слишком высоким, а справа появляется большое пустое пространство.

Пример из ТЗ: `/product/product-111825`.

### Требуется

- сделать галерею/карусель миниатюр;
- дать возможность листать изображения;
- ограничить/зафиксировать высоту области миниатюр;
- сохранить выбор основного изображения товара;
- проверить адаптив.

### Готово, когда

Карточка товара с большим количеством изображений не растягивается по высоте из-за списка миниатюр, а все изображения доступны через управление галереей.

## PE-04 — Корректировка хлебных крошек

**Приоритет:** 🔴 P1  
**Статус:** TODO  
**Зона:** `e-commerce`, возможно `ecommerce-backend`

### Проблема

При переходе из карточки товара по промежуточному пункту хлебных крошек контекст категории теряется.

Пример из ТЗ:

- товар: `/product/product-2150704705`;
- переход по `PlayStation 5 Slim` ведёт на `/catalog/playstation-5-slim`;
- после перехода цепочка сокращается до `Главная > Каталог > PlayStation 5 Slim`.

### Требуется

Сохранять полную и корректную иерархию хлебных крошек. Для примера из ТЗ ожидаемый контекст включает:

`Главная > Каталог > Sony > Приставки > PlayStation 5 Slim`.

Нужно проверить не только конкретный пример, а общий механизм построения breadcrumbs для каталога и карточки товара.

### Готово, когда

Переходы по хлебным крошкам не теряют родительские уровни каталога и отражают реальную иерархию.

## PE-06 — HTML-редактирование статей

**Приоритет:** 🔴 P1  
**Статус:** ✅ DONE  
**Дата выполнения:** 06.09.2026  
**Зона:** `e-commerce-admin`

### Проблема

Текущий редактор не даёт удобно работать с HTML и сложной разметкой. В частности, невозможно нормально добавлять таблицы; две имеющиеся кнопки в редакторе, по наблюдению клиента, работают практически одинаково.

### Требуется

- дать возможность добавлять и редактировать HTML статьи;
- обеспечить работу таблиц и другой необходимой HTML-разметки;
- не ломать существующий визуальный редактор и уже сохранённые статьи;
- проверить безопасное сохранение и вывод HTML.

### Выполнено 06.09.2026

- вместо старых `toggleCode()` / `toggleCodeBlock()` сделан настоящий режим редактирования HTML-исходника;
- переключатель HTML перенесён вправо;
- в HTML-режиме иконка меняется с `</>` на «глаз» для возврата в визуальный редактор;
- добавлен полноэкранный режим редактора;
- `Esc` закрывает полноэкранный режим;
- HTML отображается на светлой теме с подсветкой синтаксиса;
- при входе в HTML-режим код автоматически форматируется с переносами и отступами по 2 пробела;
- клавиша `Tab` в HTML-режиме вставляет 2 пробела;
- содержимое не теряется при переключении HTML ↔ визуальный режим;
- сохранение осталось через существующее поле `text`, без изменения backend API;
- проверено, что storefront уже выводит `post.text` как HTML.

### Готово, когда

Редактор позволяет быстро подготовить полноценную статью, включая таблицы и необходимую разметку.

# PE-13 — Уникализация описаний товаров через ИИ

**Приоритет:** 🔴🔴 P0 — в первую очередь  
**Статус:** TODO  
**Зона:** `e-commerce-admin`, `ecommerce-backend`

## Критически важное ограничение текущего этапа

В объединённом ТЗ прямо указано, что **сейчас согласована простая версия уникализации описаний через ИИ**. Полный функционал, описанный ниже в исходном документе, пока **не входит автоматически в текущую реализацию**.

То есть сначала делаем небольшой MVP и проверяем его на демоверсии/локальной среде. Расширенную автоматизацию реализуем только после отдельного согласования.

## Цель MVP

Получать на основе существующих данных товара уникализированное описание через API выбранной нейросети без выдумывания отсутствующих характеристик.

### Входные данные

Минимально использовать:

- название товара;
- категорию;
- характеристики;
- существующее описание, если оно есть.

### Базовые требования к тексту из полного ТЗ

Полное ТЗ предлагает ориентир:

- 500–1000 символов;
- 2 абзаца;
- естественное SEO-вхождение названия товара;
- экспертный, уверенный тон;
- не придумывать характеристики;
- без скрытых допущений;
- без служебных вводных фраз нейросети.

### Что нужно определить до реализации MVP

- какой AI API используем;
- где хранится API key;
- какие действия доступны из админки на первом этапе;
- нужна ли автоматическая запись результата сразу в описание или сначала preview/подтверждение;
- как маркируем текст, созданный ИИ.

## Полный функционал из ТЗ — резерв следующего этапа

Ниже перечислено для сохранения требований, но **не считаем это автоматически согласованным объёмом MVP**:

- массовая обработка около 2000 товаров;
- очередь запросов и rate limits;
- автоматическая проверка длины 500–1000 символов и повторный запрос на корректировку;
- стоп-слова;
- очистка Markdown/нормализация кавычек;
- статус `requires_manual_input` для товаров без данных;
- логирование `success / error / requires_manual_input`;
- отметка «сгенерировано ИИ» и фиксация последующего ручного редактирования;
- дата/время генерации и ручного изменения;
- автогенерация для новых товаров;
- генерация конкретного товара;
- генерация всех товаров;
- генерация только товаров без описания;
- перегенерация AI-описаний, в том числе по периоду;
- редактируемые промпты в настройках;
- настройка `temperature`;
- тестирование сначала на небольшой выборке, затем перенос на production.

### Готово для MVP, когда

На тестовом товаре из админки можно безопасно получить уникализированное описание из существующих данных товара, проверить результат и сохранить его без обращения к production-интеграциям.

# Правило работы по задачам

Для каждой фактически выполняемой клиентской задачи:

1. создаём отдельную ветку `task/pe-XX-short-name`;
2. не меняем несвязанную существующую логику;
3. фиксируем изменения небольшими тематическими коммитами;
4. проверяем локально на восстановленной локальной БД;
5. после проверки помечаем задачу в этом файле как `DONE` и указываем дату выполнения;
6. локальные dev-fixes и инфраструктурные изменения не смешиваем с клиентской поставкой.
