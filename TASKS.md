## PE-01 — Галерея изображений товара

**Приоритет:** 🟢 P3  
**Статус:** ✅ DONE  
**Дата выполнения:** 06.09.2026  
**Зона:** `e-commerce`

### Проблема

Если у товара много изображений, миниатюры выводятся длинным вертикальным столбцом. Из-за этого блок карточки становится слишком высоким, а справа появляется большое пустое пространство.

Пример из ТЗ: `/product/product-111825`.

### Требуется

- сделать галерею/карусель миниатюр;
- дать возможность листать изображения;
- ограничить/зафиксировать высоту области миниатюр;
- сохранить выбор основного изображения товара;
- проверить адаптив.

### Выполнено 06.09.2026

- область миниатюр ограничена по высоте и синхронизирована с основной областью изображения;
- добавлена прокрутка миниатюр стрелками;
- на десктопе миниатюры листаются вертикально, на мобильных — горизонтально;
- прокрутка выровнена по целым миниатюрам без обрезанных карточек;
- выбор основного изображения сохранён;
- поведение подготовлено совместно с PE-15.

### Готово, когда

Карточка товара с большим количеством изображений не растягивается по высоте из-за списка миниатюр, а все изображения доступны через управление галереей.

## PE-03 — Вывести категорию Sony в плитке категорий

**Приоритет:** 🟢 P3  
**Статус:** ✅ CLOSED — клиент согласовал оставить текущее поведение  
**Дата решения:** 13.09.2026  
**Зона:** `e-commerce`, при необходимости `e-commerce-admin` / `ecommerce-backend`

### Требуется

На странице `/categories` добавить в общую плитку категорию, ведущую на `/catalog/sony`.

### Диагностика 06.09.2026 — без правок кода

Проверен текущий механизм вывода категорий.

- галочка **«Показывать в главных категориях»** в админке сохраняет у категории `isMain = true`;
- после сохранения backend инвалидирует кеш категорий, поэтому проблема не связана со старым кешем;
- страница `/categories` получает список из endpoint `/categories/main`;
- backend включает туда активные, не удалённые категории с `isMain = true` и сортирует их по `mainSortOrder`;
- затем storefront дополнительно скрывает категории, у которых `productCount = 0`;
- `productCount` считается по активным товарам, связанным с категорией или её дочерними категориями через связи `ProductCategory`;
- наличие у товара бренда Sony само по себе не увеличивает `productCount` категории Sony;
- поэтому `/catalog/sony` может показывать товары через brand-контекст, а сама категория Sony при этом оставаться пустой с точки зрения связей категорий.

**Подтверждено на текущих данных:** категория Sony пустая, поэтому при `isMain = true` она всё равно не выводится в общей плитке.

То есть администратор ставит галочку правильно — категория скрывается уже на storefront из-за правила «не показывать главные категории без товаров».

### Решение клиента 13.09.2026

Клиент согласовал **оставить текущую механику как есть**. Изменения в код для PE-03 не требуются. Категория Sony при `productCount = 0` остаётся скрытой в плитке главных категорий.

Задача закрыта по согласованию клиента без доработки кода.

## PE-04 — Корректировка хлебных крошек

**Приоритет:** 🔴 P1  
**Статус:** ✅ DONE  
**Дата выполнения:** 15.09.2026  
**Зона:** `e-commerce`, возможно `ecommerce-backend`

### Проблема

При переходе из карточки товара по промежуточному пункту хлебных крошек контекст категории теряется.

Пример из ТЗ:

- товар: `/product/product-2150704705`;
- переход по `PlayStation 5 Slim` ведёт на `/catalog/playstation-5-slim`;
- после перехода цепочка сокращается до `Главная > Каталог > PlayStation 5 Slim`.

### Диагностика 13.09.2026

В админке категория `PlayStation 5 Slim` сохранена как корневая: поле «Родительская категория» установлено в «Без родительской категории».

Страница категории строит breadcrumbs по реальному дереву `parentId`, поэтому при текущих данных может корректно вывести только:

`Главная > Каталог > PlayStation 5 Slim`.

Карточка товара использует дополнительный контекст категорий товара, поэтому там может присутствовать более длинная цепочка.

### Решение

Задача по хлебным крошкам закрыта после приведения структуры категорий и навигационного контекста к согласованному состоянию.

### Готово, когда

Переходы по хлебным крошкам не теряют родительские уровни каталога и отражают реальную иерархию.

**Приоритет:** 🔴 P1  
**Статус:** ✅ DONE  
**Дата выполнения:** 06.09.2026  
**Зона:** `e-commerce-admin`

### Проблема

Текущий редактор не даёт удобно работать с HTML и сложной разметкой. В частности, невозможно нормально добавлять таблицы; две имеющиеся кнопки в редакторе, по наблюдению клиента, работают практически одинаково.

### Требуется

- дать возможность добавлять и редактировать HTML статьи;
- обеспечить работу таблиц и другой необходимой HTML-разметки;
- не ломать существующий визуальный редактор и уже сохранённые статьи;
- проверить безопасное сохранение и вывод HTML.

### Выполнено 06.09.2026

- вместо старых `toggleCode()` / `toggleCodeBlock()` сделан настоящий режим редактирования HTML-исходника;
- переключатель HTML перенесён вправо;
- в HTML-режиме иконка меняется с `</>` на «глаз» для возврата в визуальный редактор;
- добавлен полноэкранный режим редактора;
- `Esc` закрывает полноэкранный режим;
- HTML отображается на светлой теме с подсветкой синтаксиса;
- при входе в HTML-режим код автоматически форматируется с переносами и отступами по 2 пробела;
- клавиша `Tab` в HTML-режиме вставляет 2 пробела;
- содержимое не теряется при переключении HTML ↔ визуальный режим;
- сохранение осталось через существующее поле `text`, без изменения backend API;
- проверено, что storefront уже выводит `post.text` как HTML.

### Готово, когда

Редактор позволяет быстро подготовить полноценную статью, включая таблицы и необходимую разметку.

## Согласованный MVP

Вместо первоначального большого AI-модуля реализован компактный рабочий функционал в админке:

- по кнопке «Вставить в описание» AI-текст переносится в обычное поле описания;

- можно просматривать старый и новый текст, применять отдельные варианты и все готовые варианты;
- существующие описания не заменяются до явного подтверждения.

## GEN API и правила текста

В модель передаются фактические данные товара:

- название;
- бренд;
- категории;
- характеристики;
- существующее описание.

Промпт запрещает придумывать отсутствующие характеристики, комплектацию, гарантии, совместимость и другие факты.

Целевой формат:

- 500–1000 символов;
- 2 смысловых абзаца;
- естественное использование названия товара;
- без Markdown;
- без служебных вводных фраз.

Если первая генерация не проходит проверку длины/формата, выполняется одна автоматическая попытка исправления. Неидеальный результат после повторной попытки сохраняется для ручной проверки, а не применяется автоматически.

## Безопасность

- GEN API вызывается только backend-сервисом;
- полный API key не возвращается во frontend после сохранения;
- ключ хранится зашифрованным;
- AI-черновик хранится отдельно от `Product.description` до применения.

### Проверено 13.09.2026

- GEN API настройки сохраняются;
- генерация отдельного товара работает;
- AI-черновик выводится в карточке товара;
- «Вставить в описание» переносит AI-текст в штатное поле описания;
- после обычного сохранения товара новое описание сохраняется корректно;
- существующее описание не меняется самопроизвольно до явного действия пользователя.

Расширенные сценарии автоматизации новых товаров, редактор промпта, temperature и другие настройки остаются резервом Phase 2 и не входят в текущую задачу.
